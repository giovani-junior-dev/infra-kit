Purpose

Dar aos alunos da comunidade a mesma infraestrutura que roda o WaBlast hoje, sem Supabase e sem serviço de terceiros no caminho dos dados: Docker Swarm + Portainer, Postgres de produção, Postgres de homologação (pg-homolog), backups com PG Back Web, e o db-mcp (MCP de banco com guardrails e aprovação do dono) acessível pelo Claude Code do aluno. Tudo instalado por um repositório público de scripts idempotentes, conduzido por um plugin do Claude Code.

Decisões do dono (2026-10-10): 1 servidor por padrão (opção de separar o banco depois) · Ubuntu 24.04 como única referência testada · domínio na Cloudflare obrigatório · kit público.

Problem

A maioria dos alunos depende de Supabase e outros SaaS: custo que cresce com o uso, limites do plano grátis, dado fora do controle deles. Montar a alternativa sozinho é onde eles quebram: Postgres exposto na internet, senha escrita na stack, SSH com root e senha, sem backup testado, sem separação entre homologação e produção. Nós mesmos tropeçamos nisso (incidentes de 2026-06-28 e 2026-10-10). E um agente de IA com acesso de superuser ao banco de produção é um risco que a maioria nem percebe.

Solution

Um repositório público infra-kit com três camadas:

  1. Scripts idempotentes por etapa (bash, rodam no servidor) + stacks Docker prontas. Rodar duas vezes não estraga nada; cada etapa termina com uma verificação.
  2. db-mcp extraído do monorepo do WaBlast para um pacote próprio, genérico, publicado como imagem Docker (ghcr.io). Sobe como mais uma stack.
  3. Plugin do Claude Code com 4 skills (/infra:instalar, /infra:verificar, /infra:novo-projeto, /infra:trocar-senha) que entrevistam o aluno, rodam os scripts por SSH em ordem e explicam cada erro em português simples.

Princípio de rede: zero porta pública além do SSH. Portainer, PG Back Web e db-mcp ficam atrás de Cloudflare Tunnel (saída do servidor, sem porta de entrada) + Cloudflare Access. Postgres nunca é alcançável de fora.

2.3. 15-ssh-hardening.sh com trava anti-lockout

# drop-in que vence os arquivos do cloud-init (ordem alfabética, 1º valor vence)
cat >/etc/ssh/sshd_config.d/00-infra-kit.conf <<EOF
Port ${KIT_SSH_PORT}
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
AllowUsers ${KIT_ADMIN_USER}
EOF
sshd -t                         # config inválida → aborta sem recarregar
ufw allow ${KIT_SSH_PORT}/tcp   # ANTES de recarregar
systemctl reload ssh            # reload: sessões abertas continuam
# a skill abre UMA NOVA conexão com a chave na porta nova antes de seguir;
# falhou → rollback automático (remove o drop-in, reload) e avisa
  • [] Ubuntu 24.04 usa socket activation do ssh: tratar ssh.socket ao mudar a porta (validar no e2e)
  • [] UFW: default deny incoming, allow só $KIT_SSH_PORT

2.4. 20-docker-swarm.sh

  • [] Docker CE pelo repo oficial (não o docker.io do Ubuntu); log driver json-file com max-size=20m,max-file=5
  • [] docker swarm init --advertise-addr <ip privado ou público>; rede overlay attachable infra_net
  • [] Docker ignora o UFW para portas publicadas. Regras na chain DOCKER-USER: drop de todo tráfego de entrada vindo da interface pública para containers, exceto conexões já estabelecidas. Persistidas por unit systemd que roda após o docker

Alternativas rejeitadas

  • Só skill (sem scripts): cada aluno ganha uma instalação diferente; impossível dar suporte.
  • Ansible: mais robusto, mas mais uma ferramenta para o aluno leigo; bash idempotente + verificação cobre 1 servidor. Reavaliar se surgir multi-servidor.
  • Coolify/Dokploy: resolveriam deploy de app, mas não o db-mcp nem o modelo de segurança; dá para conviver depois.
  • Postgres com porta aberta e allowlist: é o que temos no WaBlast por causa dos 2 servidores; para aluno, o risco de errar a allowlist não compensa.
